
The bug was a race between fragile input handling and unsafe token assumptions. The request method relied on default parameters (options = {}) which can be stripped or mishandled during transpilation, causing options to arrive as undefined. Consequently, if (options.api) failed silently, skipping the Authorization header injection. Additionally, the code assumed the refreshed token always exposed accessToken without runtime validation.

It happened because TypeScript's compile-time guarantees don't survive all runtime environments. The test passed { api: true }, but if the function signature's default parameter wasn't applied (e.g., due to loose this binding or Babel target misconfiguration), the conditional check evaluated against undefined, not {}.

The fix normalizes inputs explicitly: options? with const opts = options || {} guarantees an object, and opts.api === true enforces strict boolean logic. We also added 'accessToken' in token before header assignment, ensuring we never interpolate undefined. This shifts trust from the compiler to defensive runtime checks critical for library code consumed in unpredictable environments.

One edge case still untested: clock skew. The expired getter compares expiresAt against Date.now(). If the client clock drifts +5 minutes relative to the auth server, a "valid" token will be rejected upstream. Production code should add a refresh buffer (e.g., expiresAt - 300s) and ideally sync time via NTP or HTTP headers. Tests should mock Date.now() to verify behavior under skew.
